*go-asm.txt*  Assembly language server with live emulation and debugging

                                                                     *go-asm*
go-asm.nvim ~

A Neovim client for the go-asm language server: it assembles NASM/Intel-syntax
assembly live, runs it in an emulator, and shows register state inline.
Targets x86-64, 32-bit x86 (BITS 32) and RISC-V, auto-detected per buffer.

Requires Neovim 0.11+ and, for |:GoAsmInstall|, curl.

0. SYNTAX                                                     *go-asm-syntax*

go-asm follows NASM conventions — NASM/Intel syntax, not GNU as or MASM. The
assembler is checked against nasm's own output.

    comments        ; like this        (not #, //, or /* */)
    address of msg  mov rsi, msg
    contents of msg mov al, [msg]      (MASM would write "mov al, msg")
    operand order   mov dst, src       (not AT&T's src, dst)
    registers       rax, eax           (not %rax)
    immediates      5  0x1f  1Fh  1010b  17o      (not $5)
    sized memory    mov byte [x], 1    (not movb)

Square brackets mean dereference; their absence means the address. That
explicitness is the main difference from MASM.

db/dw/dd/dq, labels with or without a colon, section, global, extern and
BITS 32 work as nasm defines them. `equ` and `$` are not implemented yet.

What is supported ~
Verified against the assembler, not aspirational.

  directives    BITS 32/64, section, segment, global, extern, cpu,
                "default abs", align, alignb, equ (including "equ $-msg")
                not yet: org, times, incbin

                "default rel" and BITS 16 are refused, not ignored: each
                changes how the whole program is encoded, so accepting them
                quietly would produce code that does not do what it says.

  preprocessor  object-like %define only. Substitution is whole-word and skips
                string literals, so a macro named N rewrites neither COUNT nor
                the N in "db 'N'". The directive is case-insensitive (%DEFINE),
                as in nasm; macro names are not.
                not yet: %define f(a), %macro, %assign, %if, %include — each
                reports itself rather than failing as a bad operand

  expressions   + - * / % << >> & | ^ ~ and parentheses, over literals,
                symbols, character constants ('A'), $ (here) and $$ (section
                start). Values track relocatability as nasm does: an address
                moves with the load address, "end-start" is a length and does
                not, and adding two addresses is an error.

  data          db dw dd dq (strings in ' or ", commas and semicolons inside
                them), resb resw resd resq
                not yet: dt do dy dz, backtick strings with \n escapes

  labels        "msg:" or colonless "msg db 1", local labels (.loop), forward
                references. A bare label is its address; [msg] and [rel msg]
                are its contents.

  registers     rax..r15 in every width (r8d/r8w/r8b), high-byte ah/ch,
                spl/bpl/sil/dil
                not yet: segment registers, xmm/ymm/zmm

  memory        [reg], [reg+disp], [base+index*scale+disp], [label],
                [rel label], byte/word/dword/qword ("ptr" accepted and
                ignored), 32-bit addressing under BITS 32

  immediates    5, 0x1f, 1Fh, 0b101, 101b, 0o17, 17o, negatives
                not yet: the "strict" keyword

  instructions  data movement, arithmetic, logic, jmp/jcc (short and near, as
                nasm chooses), the loop family, call/ret, push/pop, setcc,
                cmovcc, imul (including nasm's "imul reg, imm" shorthand),
                movzx/movsx, mul/div, shifts, bsf/bt, cpuid, hlt, syscall,
                int, rep/lock prefixes

                Encoding is checked against nasm itself: a sweep assembles
                every general-purpose form in nasm's table and compares
                bytes, currently matching 86.8%. The shortfall is almost all
                APX/EVEX/VEX/XOP, not classic instructions.

  running       Linux syscalls through both the x86-64 "syscall" gate and the
                32-bit "int 0x80" gate: write, exit, read. Output appears
                inline under the program as you run or step.

                A small set of libc entry points is stubbed for "extern" —
                printf, puts, putchar, exit — covering %d %i %u %x %X %o %c
                %s %p %%, in both the SysV register convention and 32-bit
                cdecl. There is no linker: these are emulated, and the set is
                deliberately output-only. Nothing allocates, reads input, or
                manipulates strings.

An instruction the encoder does not reach yet is reported as a hint rather
than an error, so a coverage gap never paints working code red.

Where this differs from nasm ~
Two differences are deliberate rather than gaps, and both matter because the
code assembles either way.

Sections are not reordered. nasm groups output by section — .text, then .data,
then .bss — whatever order they appear in the source. go-asm emits in source
order, because it produces one flat image for the emulator to load rather than
an object file for a linker. A program that writes .data first therefore gets
different addresses here than nasm would give it. It still runs correctly:
"global main" (or a main/_start label) sets the entry point, so execution
starts in the right place rather than in the string constants.

"mov reg, label" may encode shorter. nasm loads a relocatable address with the
10-byte "mov r64, imm64" form because it cannot assume the address fits in 32
bits; go-asm knows the final address and uses the 5-byte imm32 form when it
fits. Same value in the register, fewer bytes.

Neither affects whether a program behaves correctly here. Both mean the byte
stream is not always identical to "nasm -f bin".

File extensions ~
The plugin attaches on the `asm` and `nasm` filetypes, which cover .asm,
.nasm, .s and .S — there is no extension list to configure. Note that .S
conventionally means GNU as source: such a file attaches and is then flagged
line by line ("unknown instruction: .text"), because the dialect differs.
GNU as directives are not implemented on any target, and on x86 neither is
AT&T syntax.

Comment characters follow each target's own convention:

    x86 / x86-64    ;
    RISC-V          #  ;
    ARM64           // #(leading) ;

Programs may use Linux syscalls: write, exit and read are emulated through
both the x86-64 `syscall` gate and the 32-bit `int 0x80` gate, and anything
written to stdout appears inline under the program.

1. INSTALL                                                   *go-asm-install*

With lazy.nvim: >lua

    {
      "SorinS/go-asm",
      lazy = false,
      build = ":GoAsmInstall",
      config = function() require("go_asm") end,
    }
<
Loading eagerly is deliberate: require("go_asm") only registers autocommands
and commands — no server starts until an .asm file is opened — whereas
lazy-loading on ft leaves |:GoAsmInstall| and `:checkhealth go_asm` undefined
until then, which is exactly when they are needed.
The server is a prebuilt binary published on GitHub Releases. |:GoAsmInstall|
downloads the build for your platform into `stdpath("data")/go-asm/bin` — no
sudo, no PATH changes, no Go toolchain.

Builds exist for darwin-arm64, darwin-amd64, linux-amd64, linux-arm64 and
windows-amd64.

2. COMMANDS                                                 *go-asm-commands*

                                                              *:GoAsmInstall*
:GoAsmInstall [tag] Download the go-asm server for this platform. With no
                    argument, installs the version this plugin expects (see
                    |go-asm-versioning|). Pass "latest" for the newest
                    release, or a tag like "v0.1.0" for a specific one. Safe
                    to re-run; it overwrites the existing binary.

                                                                  *:GoAsmRun*
:GoAsmRun [args]    Run the buffer, passing args to the program as its command
                    line. argv[0] is the file name, so ":GoAsmRun 5 10" gives
                    the program an argc of 3.

                    Where the arguments arrive depends on the entry point, as
                    it does on a real system: a program entered at _start
                    finds argc on top of the stack and the argv pointers above
                    it; one entered at main takes argc and argv in rdi/rsi, or
                    above the return address in 32-bit.

                    With no args the stack is left untouched, which is not the
                    same as an empty command line: a program that pops argc
                    sees exactly what it saw before. The <leader>rr
                    mapping always runs this way.

                                                                *:GoAsmDebug*
:GoAsmDebug [args]  Start a debug session with those arguments, replacing any
                    session on the buffer. Stepping, continuing and restarting
                    reuse them; only starting a new session can change them.

                                                                 *:GoAsmInfo*
:GoAsmInfo          Show the resolved binary path, its version, the detected
                    platform and the release repo.

                    See also `:checkhealth go_asm`.

==============================================================================
3. MAPPINGS                                                 *go-asm-mappings*

Set on the buffer when the server attaches; nothing is bound globally.

Run: ~
    <leader>rr      Run the buffer.
    <leader>rc      Run to the cursor line.
    <leader>rg      Toggle the registers panel — a vertical split on the
                    right showing the full register file. It refreshes after
                    every run and every step, so it can be left open while
                    stepping. `q` closes it from inside.
    <leader>rx      Toggle the inline overlay.
    K               Hover: encoded bytes and operand forms.

Debug: ~
    <leader>rs      Step one instruction.
    <leader>ro      Step over.
    <leader>rS      Step back.
    <leader>rR      Restart the session.
    <leader>rn      Continue to the next breakpoint.
    <leader>rq      Quit debugging and clear.
    <leader>rb      Toggle a breakpoint.
    <leader>rB      Conditional breakpoint; prompts for "<reg> <op> <value>",
                    e.g. "rcx == 0". Repeat on the same line to remove.
    <leader>rm      Memory dump; prompts for a register name or 0xADDR.

The memory dump is a float: it closes on q, <Esc>, or cursor movement.

4. CONFIGURATION                                              *go-asm-config*

Nothing needs configuring for normal use. Two escape hatches, set before the
server starts (before opening an .asm buffer): >lua

    local go_asm = require("go_asm")
    go_asm.cmd  = "/path/to/go-asm"   -- pin a specific binary
    go_asm.repo = "you/your-fork"     -- install from a fork's releases
<
                                                          *go-asm-versioning*
The plugin and server are released together under one tag, and the plugin pins
the server build it was written against (`require("go_asm").version`).
|:GoAsmInstall| fetches exactly that. The two share custom methods (asm/run,
asm/debug/*), so a mismatched pair shows up as failing requests rather than as
an obvious version error — `:checkhealth go_asm` compares them and warns.

Update both together: your plugin manager, then |:GoAsmInstall|.

                                                          *go-asm-resolution*
The binary is resolved in order:

    1. go_asm.cmd                      an explicit choice, always wins
    2. stdpath("data")/go-asm/bin      what :GoAsmInstall fetched
    3. PATH
    4. ~/.local/bin, ~/bin, ~/go/bin

The installed copy outranks PATH deliberately: the plugin fetches a server
matching the release it pins, and an unrelated go-asm earlier on PATH would
shadow it, giving a mismatched pair whose symptom is asm/* requests behaving
oddly rather than anything that looks like a version problem. The absolute
fallbacks matter because a GUI-launched Neovim inherits no shell PATH.

If the attached server reports a different version from the one this plugin
expects, it says so once per session and names the file it is running.

To rebind, map the module functions directly: >lua

    vim.keymap.set("n", "<F5>", function() require("go_asm").run() end)
<
Available: run(), run_to_cursor(), registers(), clear(), dbg_step(),
dbg_stepover(), dbg_stepback(), dbg_restart(), dbg_continue(), dbg_stop(),
toggle_breakpoint(), cond_breakpoint(), memory(), install(), binary(),
platform().

5. TROUBLESHOOTING                                   *go-asm-troubleshooting*

Nothing happens; no mappings exist ~
    The mappings are created on LspAttach, so if the server did not start,
    none of them exist. Run `:checkhealth go_asm`, then |:GoAsmInstall|.

"server binary not found" ~
    Run |:GoAsmInstall|. If you installed the binary manually, put it on PATH
    or in one of the directories under |go-asm-resolution| — note that a
    GUI-launched Neovim does not inherit your shell PATH.

"no release build for <os>/<arch>" ~
    No binary is published for that platform yet. Open an issue; meanwhile,
    point `go_asm.cmd` at a server binary you already have.
